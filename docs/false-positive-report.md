# False-positive / false-negative report

Generated by `test/corpus.test.ts` against the shipped rules in
`rules/*.yaml`, as of 2026-09-17.

## Method

Two hand-built corpora, checked into `test/fixtures/`:

- **`legit-corpus.yaml`** (26 entries): everyday git/npm/source-edit/network
  actions that must decide `allow`. Any non-`allow` result on this corpus
  is a **false positive**.
- **`malicious-corpus.yaml`** (9 entries): one case per shipped rule, plus
  a compound case exercising cumulative scoring (Phase 6). Each entry
  declares the decision it must produce (`ask` or `deny`). A result of
  `allow` on this corpus is a **false negative**.

Both corpora run through the real `loadCompiledRules()` + `evaluate()` +
`decide()` pipeline against the actual files in `rules/`, not a mock —
this is the same code path the Claude Code adapter runs in production.

## Tuning that got us here

Before writing the corpus, reasoning through `credential-file-write`'s
regex against plausible legitimate paths surfaced two real false
positives, fixed in `rules/credential-file-write.yaml` before the corpus
ever ran:

1. **`.env.example` / `.env.sample` / `.env.template`** — these are
   committed template files with no real secrets, but the old pattern
   `(^|\/)\.env(\.|$)` matched any `.env.*` file. Fixed with a negative
   lookahead: `\.env(\.(?!example|sample|template)[\w-]+)?$`.
2. **`id_rsa.pub` / `id_ed25519.pub`** — public keys are safe to write
   and commonly appear in test fixtures (e.g.
   `test/fixtures/id_rsa.pub`), but the old pattern matched the bare
   substring `id_rsa` regardless of extension. Fixed with
   `id_rsa(?!\.pub)\b` (same for `id_ed25519`). Note this only helps
   outside a `.ssh/` directory — a `.pub` file that actually lives in
   `.ssh/` is still flagged via the separate `\.ssh\/` alternative,
   which is intentional (flag the directory, not just the filename).

Also verified by direct reasoning (not corpus entries, since they'd be
redundant, but documented here for future readers): `eval $(ssh-agent -s)`
— an extremely common, legitimate shell idiom — does not match
`eval-exec-usage`'s `eval\s*\(` pattern, because there's no literal `(`
directly after `eval`/whitespace (`$(` intervenes). It's in the legit
corpus (`test/fixtures/legit-corpus.yaml`) to keep this a guaranteed
regression check rather than just a comment.

## Known gap (documented, not fixed here)

`dangerous-rm` only recognizes short combined flags (`-rf`, `-fr`) and a
fixed set of broad targets (`/`, `~`, `*`, `..`, `$HOME`). It does not
catch `rm --recursive --force /` (long-form flags) or narrower-but-still
destructive targets like `rm -rf .git`. Widening this without
reintroducing false positives (e.g. `rm -rf ./some-real-subdir`) needs a
few more corpus entries first — left for a future rules PR rather than
guessed at here.
